评测的目标是回答一个具体问题：模型、提示词、检索或工具变化之后，用户任务是否完成得更好。先定义任务和失败代价，再选指标。

## 把业务目标拆成可检查的结果

以企业政策问答为例，不能只用「回答通顺」评价质量：

| 层次 | 检查什么 | 示例指标 |
|------|----------|----------|
| 数据 | 文档是否有效、版本是否最新 | 解析失败率、过期文档占比 |
| 检索 | 正确证据是否进入上下文 | Recall@K、MRR、nDCG |
| 生成 | 结论是否得到证据支持 | 事实支持率、引用准确率 |
| 行为 | 信息不足、越权时是否拒绝 | 正确拒答率、越权成功率 |
| 产品 | 用户能否完成任务 | 任务成功率、人工升级率 |
| 运行 | 延迟和费用是否可接受 | TTFT、P95 完成时间、单任务成本 |

Recall@K 需要有标注的相关文档集合；没有标注时，不能把向量相似度当作召回准确率。生成质量、检索质量与业务成功率应分别报告。

## 建立三套互相隔离的数据

1. **开发集**：用于改提示词、切片、阈值和路由，可以反复查看。
2. **回归集**：覆盖历史故障、正常流程和边界条件，每次发布都运行。
3. **保留测试集**：用于阶段性验收，避免针对反复查看的样例过拟合。

按用户、文档、时间或业务主体划分数据，而不是随机拆开同一段对话。同源改写的问题应进入同一分区，防止信息泄漏。

每个案例至少记录输入、用户权限、证据版本、允许的工具、预期行为和评分规则：

```json
{
  "case_id": "refund-policy-001",
  "input": "这笔订单是否可以退款？",
  "tenant": "demo-merchant",
  "allowed_tools": ["read_order", "search_policy"],
  "expected_behavior": "核验订单和政策；不直接执行退款",
  "must_cite": ["refund-policy-v3"],
  "forbidden_actions": ["issue_refund"]
}
```

实际评测使用脱敏测试数据；密钥、真实账号和资金操作权限不应进入评测集。

## 按证据强度选择评分方法

| 方法 | 适合什么 | 局限 |
|------|----------|------|
| 确定性校验 | JSON Schema、工具名、金额、必填字段 | 难以评价开放式表达 |
| 人工评审 | 高风险结论、复杂业务正确性 | 成本较高，需要评分标准 |
| 模型裁判 | 语义一致性、事实支持、成对比较 | 有位置偏差、自偏好与不稳定性 |
| 用户反馈 | 实际任务效果 | 样本有选择偏差，反馈可能延迟 |

使用模型裁判时固定裁判版本，给出证据和明确量表，随机交换候选答案顺序，并用人工样本校准。不要让被测答案中的指令影响裁判，也不要把裁判分数视为客观真值。

## 定义发布门槛

门槛由业务失败代价决定。例如测试环境可以要求：权限隔离用例全部通过，退款工具不得未授权执行，核心问答正确率不低于已上线基线，P95 延迟和成本不超预算。

这些数值应写入版本化配置。严重安全用例单独判定，不能用大量简单题的高平均分抵消一次资金操作越权。

同一批案例同时比较候选版本和基线，记录逐题差异、样本量与置信区间。样本太少、两者差异很小时，应先扩大验证范围。

## 实战验收

交付一个包含正常问答、无答案、权限拒绝、工具超时、恶意文档和超长输入的评测集。报告应能回答：哪些案例变好、哪些变差、变化来自哪里、是否允许上线。
