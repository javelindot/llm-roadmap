实时语音产品需要同时处理收音、识别、推理、合成、播放和打断。先确定任务是否需要实时双向语音，再选择模型与通信方式。

## 两种主要架构

| 架构 | 链路 | 取舍 |
|------|------|------|
| 级联 | 音频 -> ASR -> 文本模型 -> TTS | 中间文本可审计、组件可替换，延迟会累积 |
| 端到端 | 多模态模型直接处理语音并产生语音 | 可保留语气等信号，审核和状态控制需要专门设计 |

客户服务可先用级联方案验证业务，低延迟对话再评估端到端方案。金融指令中的币种、金额、收款人仍需结构化校验和用户确认；识别出一句「转十块」不能直接执行付款。

## 处理回合与打断

1. 用 VAD 判断语音活动，必要时加入语义级结束检测。
2. 为每个回合分配 turn_id，区分识别中的临时文本和确认后的最终文本。
3. 用户开口时停止当前音频播放，并取消或暂停对应生成任务。
4. 清理尚未播放的音频，标记被打断的回合。
5. 上下文只记录用户实际听到的内容，避免模型以为整段回答已播完。

VAD 过于敏感会频繁截断，过于保守会让对话等待太久。根据环境噪声、语言和用户停顿习惯评估，不能只在安静实验室测延迟。

## 音频与媒体链路

浏览器媒体访问通常需要安全上下文和用户授权；本地 localhost 可用于开发。确认麦克风权限拒绝、设备切换、采样率、声道和编码格式的行为。

WebRTC 适合媒体传输；WebSocket 也能承载音频，但需要自行处理背压、缓冲和实时性。设置播放缓冲上限，避免网络恢复后播放积压的过期音频。

长期 API 密钥保留在服务端。需要客户端直连时使用供应商支持的短时凭证，并约束权限、会话和有效期；连接建立方式以供应商当前文档为准。

## 图片与文件也需要可追溯数据

保存文件 ID、页码、OCR 结果、时间戳和来源。扫描件、图表和视频帧的模型描述可能出错，应允许查看原始证据。

涉及工单、付款或隐私时，不能把图中的文字当成可信系统指令。摄像头和录音只在用户明确开启的会话内使用，按产品约定控制保存时间和删除能力。

## 单独评估实时体验

| 维度 | 示例指标 |
|------|----------|
| 识别 | WER/CER、金额和实体准确率 |
| 回合 | 错误打断率、长停顿误判率 |
| 延迟 | 语音结束到第一段可播放回答、打断生效时间 |
| 内容 | 任务成功率、工具参数准确率、证据支持率 |
| 运行 | 单分钟成本、断连恢复率、失败升级率 |

用真实口音、背景噪声、多人说话和不同设备测试。给出数字前需说明测试语言、样本量、网络条件及计时边界。

## 近期研究：语音体验与业务完成一起测

[τ-Voice，2026](https://arxiv.org/abs/2603.13686)将可核验任务、全双工交互和真实音频条件放在同一环境中。其结论提示：同一业务在文本模式表现良好，并不证明接上语音后仍能正确完成。

本项目应分别测试文本基线、级联语音和端到端语音，固定业务规则与工具权限，改变口音、噪声、停顿和打断条件。除识别和延迟外，检查订单编号是否正确、确认是否完成、动作是否重复、用户实际听到的结果是否对应真实回执。

例如客户在确认前打断并改口，旧回合不得触发提交；已发出的动作收到迟到回执时，继续核对业务事实，不能因音频播放取消就视为写入撤销。论文中的基准数字不直接作为本项目验收目标。

## 实战验收

完成一个只读语音客服：用户询问订单，系统取得授权后查状态，再播报可核验结果。订单服务超时则明确说明无法确认，用户打断后立即停止旧回答，写操作转入结构化确认页面。
