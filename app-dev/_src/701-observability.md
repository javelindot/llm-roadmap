一次用户请求可能经过鉴权、排队、检索、重排、模型生成和多次工具调用。只记录 HTTP 成功与否，无法解释「响应慢」或「回答错」的原因。

## 用一条 trace 串起完整任务

```text
用户请求 trace_id
  -> 鉴权与限流
  -> 检索：查询、索引版本、证据 ID
  -> 重排：候选数量、耗时
  -> 模型：版本、提示词版本、token、首字延迟
  -> 工具：名称、耗时、结果状态、幂等键
  -> 校验：引用、Schema、权限
  -> 结束：完成 / 拒答 / 取消 / 超时 / 人工升级
```

使用 OpenTelemetry 等现有工具记录 trace 和 span。模型调用、工具调用和检索分别建 span；调用重试也要留下记录，才能计算真实延迟与成本。

在日志中使用证据 ID 和脱敏摘要，按需要保存正文并配置访问权限、保留时间和删除流程。高基数的 request_id、用户 ID 不宜直接作为指标标签，以免监控存储膨胀。

## 区分三种延迟

| 指标 | 定义 | 用户感受 |
|------|------|----------|
| 请求排队时间 | 收到请求到开始执行 | 系统是否繁忙 |
| TTFT | 收到请求到第一个有效文本片段 | 多久开始回答 |
| 完成时间 | 收到请求到最终成功或失败事件 | 任务多久完成 |

模型服务报告的 TTFT 可能从进入模型队列开始计算，应用的 TTFT 应覆盖上游鉴权和检索。比较两个系统时必须统一计时边界。

流式返回只改善开始展示的时间，不会自动缩短完整生成时间。监控输出 token 数、每秒输出 token、工具等待和客户端断连，才能找到具体瓶颈。

## 把成本算到用户任务

单任务成本可以拆为：

```text
模型输入 token 费用
+ 模型输出 token 费用
+ 检索、重排及工具费用
+ 基础设施分摊
+ 失败重试与人工处理费用
```

优先减少重复上下文、限制无用的工具循环、按任务难度路由、复用授权范围内的检索结果。缓存键必须包含租户、权限范围、提示词和知识版本；不同用户能看到的数据不同，不能只用问题文本作为键。

模型调用后的账单数据用于校准估算。输出上限只是单次调用边界，长期 Agent 还需要整条任务的 token、时间、工具次数和金额预算。

## 从告警走到定位

1. 先按任务类型、租户、模型和版本检查是否局部恶化。
2. 通过慢请求的 trace 区分排队、检索、生成还是工具延迟。
3. 对齐最近的提示词、索引、模型和应用发布记录。
4. 检查重试是否放大故障，必要时限流、熔断或切换到只读流程。
5. 保存脱敏故障案例，加入回归集后再恢复正常流量。

告警使用一定观察窗口和最小样本量，避免单个慢请求造成频繁切换。对外部写操作，超时可能意味着结果未知，应查询状态，而不是直接重试。

## 实战验收

人为制造一次检索超时、一次工具错误和一次模型取消。运维人员应能凭一个 trace_id 判断失败环节、已经发生的副作用、恢复方式和任务费用。
