本章在[企业知识助手](802-fullstack-project.html)的基础上扩展业务闭环。目标是提高既有流程自动化率，同时处理包含多种诉求、缺失信息和异步等待的客户问题。

## 共同案例与业务边界

客户反馈订单迟迟未完成并要求催办。助手查询授权订单，核验政策与业务状态，发现缺失材料后补问；客户确认后创建工单，等待外部更新，再核对结果并回复。无法自动处理时移交人工。

订单、材料、工单和回执使用模拟服务。模型可以理解诉求和草拟动作，身份、资料校验、流程准入及写权限由业务服务决定。

## 分工与接口

```text
聊天/业务事件 -> Case 服务：目标、事实、责任人与业务状态
  -> 流程运行时：等待、审批、预算、Run 与恢复
  -> Agent：补问、检索、选择受控能力
  -> 工具执行器：身份、参数、授权、幂等与回执
  -> 通知服务：投递与重发
  -> 评测：环境状态、过程约束与业务验收
```

| 接口 | 关键契约 |
|------|----------|
| 接收消息或业务事件 | 服务端身份、事件去重、Case 关联；一个会话可含多个问题 |
| 创建/恢复 Run | 固定配置版本，从最新可信状态装配上下文 |
| 提出动作 | 不可变参数、动作键、预览及所需批准 |
| 执行动作 | 复核当前业务状态，按动作键领取和提交 |
| 处理回调 | 验签、任务归属、去重与版本检查 |
| 转人工/恢复自动处理 | 移交所有权、证据、已发生动作和待处理条件 |
| 关闭 Case | 业务结果符合标准；发送回复只是一项投递状态 |

## 产品状态应对应真实进展

用户可见状态包括正在核验、需要补充、等待确认、已提交、等待外部结果、结果待核对和人工处理中。已提交不能展示成已解决。

确认界面显示确定的目标、参数和影响；停止界面显示已经发生的动作。重连按事件序号恢复展示，避免重复确认或重复提交。

## 四次迭代

1. **可信查询**：政策引用、订单查询、身份隔离和缺失信息处理。
2. **受控写入**：动作预览、参数绑定、审批有效期、幂等工单和回执读回。
3. **长任务处理**：持久化、客户补问、回调、取消与人工接管。
4. **效果优化**：能力路由、Skills 按需装配、轨迹评测、影子与灰度。

先用[本地业务示例](../examples/business_runtime.py)理解路由与动作账本，再接入模拟 HTTP 服务和真实模型。它是部分契约的实验代码，完整应用仍需队列、租约、鉴权、日志与界面。

## 必须验证的故障

| 场景 | 期望结果 |
|------|----------|
| 客户陈述与业务系统不一致 | 保留来源差异，核验后处理 |
| 一次消息有两个诉求 | 分别跟踪问题，避免其中一个被遗漏 |
| 写成功后响应超时 | 查同一动作回执，只创建一个工单 |
| 审批后参数变化或过期 | 拒绝沿用旧批准 |
| 两个 worker 领取同一动作 | 仅一个取得执行权 |
| 用户停止，外部动作已开始 | 显示事实，核对结果并按业务规则补偿 |
| 人工接管后收到迟到事件 | 入账必要事实，不重新夺取处理权 |
| 模型降级缺少工具能力 | 返回可解释的受控失败或合法替代路径 |
| 政策变更或用户撤权 | 重新检查证据与当前访问范围 |

## 业务指标与交付验收

统计可自动处理案例覆盖率、正确解决率、合理接管率、重复联系、业务周期、违规与重复动作、每个有效解决问题的成本。自动化率的分母应固定业务范围，并说明哪些案例依法或依规则必须人工处理。

将客户实际行动纳入验证：客户声称已补材料，必须等受控业务事件确认材料状态；客户确认提交，必须对应确定参数的有效批准。参考[近期交互式研究](003-research-map.html)，用政策、工具和用户协作组合案例验证闭环，而不是分别通过问答与工具测试就判为完成。

交付真实可运行的应用和脱敏案例集；演示正常处理、写成功后超时、人工接管三个过程。记录模型、Prompt、工具、Skill、政策和知识版本，以及回退时正在运行的 Case 如何处理。
