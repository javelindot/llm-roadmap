Harness 是模型周围的执行系统：组织上下文、提供工具、限制权限与预算、保存进度、核验结果并恢复故障。业务平台的可靠性需要由这个系统和权威业务服务共同保证。

## 明确各类状态的职责

| 对象 | 负责什么 | 不能混同什么 |
|------|----------|--------------|
| Conversation | 用户交互与渠道消息 | 一段聊天不一定只对应一个问题 |
| Case | 业务目标、事实、待满足条件、负责人 | 回复发送成功不等于问题解决 |
| Run | 一次执行的配置、步骤、预算和停止原因 | 新 Run 不代表可以重复业务动作 |
| Action | 对外操作的参数、授权、幂等键与回执 | 网络超时不等于操作失败 |
| Delivery | 回调、通知与重发记录 | 投递成功不等于业务已验收 |

Case 可以跨会话和 Run；Action 的去重标识应绑定业务动作，不能仅由瞬时模型调用 ID 决定。

## 流程与自主执行的组合

```text
消息/业务事件 -> Case -> 确定性状态与权限检查
  -> Agent 理解、补问、选择受控能力
  -> 业务服务验证并执行 -> 查询真实结果
  -> 回执与结果验证 -> 继续、等待、人工接管或关闭
```

Agent 可以解释异常、选择补充查询或草拟工单。身份认证、业务准入、金额规则、批准与最终状态变更由权威服务控制。增加模型能力不自动扩大动作权限。

## 持久化与外部副作用

checkpoint 保存应用进度，但无法与任意外部服务形成原子事务。常见故障是“业务写入成功，保存进度前崩溃”。

动作账本应保存不可变参数和指纹；执行前原子领取动作；发出请求后结果不确定时保存 unknown，并按同一业务键查询回执。外部服务也需要支持幂等，必要时使用 outbox、对账或补偿。

本地 [ActionLedger](../examples/business_runtime.py)演示参数指纹、审批有效期、原子领取与未知结果核对。它不会执行外部 API，也不提供跨服务 exactly-once、完整任务租约或审批人的身份验证；这些由集成系统补齐。

## 审批是一个明确的执行契约

审批绑定租户、问题、工具、不可变参数、审批人、有效期和策略版本。执行前重新检查身份、对象和业务状态。模型更换参数、规则变化或审批过期后，应失效并重新走合法流程。

审批文字、聊天中的“可以”和 SDK 的工具批准不是同一层的业务凭证，应用应明确各自覆盖的范围。

## 等待、取消和人工接管

| 状态 | 恢复条件 | 需要保留 |
|------|----------|----------|
| 等待客户 | 补充消息与当前问题关联 | 缺失信息及已核实事实 |
| 等待审批 | 针对确定动作的有效批准 | 参数、指纹、有效期与策略版本 |
| 等待外部系统 | 核验回调或查询任务结果 | 远程 ID、操作键和回执 |
| 结果未知 | 查询确认实际副作用 | 已发送动作与对账过程 |
| 人工接管 | 所有权按受控流程移交 | 证据、已发生动作和待处理事项 |

取消请求、执行停止和业务补偿分别记录。迟到结果可以作为动作事实入账，但不能绕过当前 Case 状态重新驱动已关闭的流程。

## 选择运行时

| 方案 | 收益 | 应用仍需负责 |
|------|------|--------------|
| 托管 Harness | 平台管理部分执行、会话和上下文 | 数据边界、业务授权、动作幂等与回执 |
| 应用内 Agent SDK | 控制部署、工具、审批与存储集成 | 持久化、队列、任务归属与恢复设计 |
| 图/工作流运行时 | 显式状态转移、等待与恢复 | 外部副作用、契约与版本迁移 |
| 直接模型 API | 自定义集成与执行循环 | 全部编排、上下文和运行治理 |

框架选型先做故障原型：进程重启、两个 worker 竞争、审批后参数变化、写成功后断网，以及人工接管后的迟到消息。满足这些契约再比较开发体验。
