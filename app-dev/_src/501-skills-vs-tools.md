**Prompt 描述要求，Tool 提供可执行能力，MCP 规范客户端与服务的交互，Skill 沉淀任务方法。** 它们可以组合，也可以独立使用。

## 职责对比

| 机制 | 主要职责 | 谁执行 | 复用方式 |
|------|----------|--------|----------|
| Prompt | 任务、约束、上下文与输出要求 | 模型生成 | 版本化模板与组件 |
| Tool / Function Call | 声明参数并请求外部操作 | 应用校验后执行 | 函数、内部 API 或服务 |
| MCP | 工具、资源、提示及协议交互 | Host/Client 与 Server | 标准连接和服务能力 |
| Skill | 步骤、判断规则、资源与验收 | 运行时按需读取并调工具 | 目录包与版本管理 |

Function Call 并不意味着业务函数必须在应用进程内；它可以调用远程 API。MCP Server 也不必须使用某家模型 SDK，其内部可以是普通 Python/HTTP 服务。MCP 不只是 Function Call 的包装，还定义资源、提示、能力协商等协议内容。

## 一个销售报告流程

1. Prompt 明确报告周期、读者和输出语言。
2. Tool 读取授权数据并用程序计算金额、环比和分组指标。
3. MCP 让多个客户端复用同一数据服务。
4. Skill 说明缺失值如何处理、哪些图表必要、如何引用与验收。
5. Workflow/Agent 负责流程状态、重试、审批和恢复。

模板有助于格式一致，但不能保证数据正确。无论有多少技能，金额计算仍应由程序完成，写入业务状态仍需执行层授权。

## 如何选择

| 需求 | 可行起点 | 引入其他机制的条件 |
|------|----------|--------------------|
| 一段文本总结 | Prompt | 重复任务可封装 Skill |
| 查询订单 | 一个只读 Tool | 多客户端共享可做 MCP |
| 季度报告 | 计算工具加版本化模板 | 方法复杂且重复时用 Skill |
| 退款流程 | 受控业务 API 与状态机 | Agent 处理理解，执行保留审批 |
| 跨产品工具平台 | MCP 与身份权限层 | 按任务附加 Skills |

不要为了层级完整而强制同时引入四者。已有内部 API 可以直接适配工具；已有可靠状态机不需要交由模型自由规划。

## 发现、加载与选择

工具定义和 Prompt 都可由运行时动态选择，不一定永远全量进入上下文。Skill 的渐进式读取是一种组织约定，不是唯一能够节省上下文的方式。

模型选择工具或技能是候选决策；服务端必须验证名称、参数、当前身份和业务状态。描述相似的技能要测试混淆率，多个同名 MCP 工具要保留服务身份。

## 组合时的边界

技能写着“发送报告”并不等于用户已经授权发送；MCP 已连接也不等于所有工具可用。把可读范围、允许操作、外部访问和人工审批分别落实在执行层。

输出协议也不能替代安全：一份符合 JSON Schema 的请求仍可能请求错误账号或越权操作。业务验证、幂等与审计都是独立要求。

## 验收练习

用同一份 CSV，分别通过普通脚本、Prompt+Tool、MCP 服务和 Skill 流程完成统计。比较代码复用、结果正确性、调用成本和失败处理；小项目不必实际部署四套系统。
