上下文工程决定每次模型调用看见什么。系统保存的全部状态、界面展示的进度和模型实际收到的信息是三个不同对象，应分别设计。

## 先明确事实与信任来源

| 信息 | 例子 | 进入上下文的规则 |
|------|------|------------------|
| 可信任务约束 | 当前租户、允许动作、预算 | 来自服务端；执行层再次检查 |
| 客户陈述 | “我已经补齐材料” | 标记为客户提供，不自动改成已核实事实 |
| 业务事实 | 订单状态与工具回执 | 保留查询时间、版本、资源标识和来源 |
| 检索证据 | 政策条款、历史处理说明 | 保留授权、有效期与可访问引用 |
| 模型推断 | “可能是材料缺失” | 保留不确定性，不能覆盖权威状态 |
| Skill 指令 | 异常处理方法 | 固定版本，权限仍由宿主控制 |

分隔符有助于模型识别来源，但并不能阻止提示注入。文档中的指令属于数据，身份、目标资源和写权限不能由模型或检索内容决定。

## 一次调用的装配顺序

```text
可信身份与任务约束
  -> 当前 Case 的目标、状态、待确认事项
  -> 已核实事实与最近有效回执
  -> 与当前步骤有关的规则、Skill、证据
  -> 必要的对话片段与工具定义
  -> 预留输出/推理预算后检查输入大小
```

预算计算包含消息模板、工具 schema、图片等开销。不同供应商对推理与输出预算的计量不同，应由模型适配层计算，不能统一把字符数当成 token 数。

仓库 [build_context](../examples/core_patterns.py)演示去重、完整证据块和输出预留。它并未实现可信来源验证、缓存或压缩；这些需要由应用在装配前完成。

## 按需加载的收益与代价

先给能力目录或证据索引，确认需求后读取正文，可以减少无关信息。固定业务步骤通常适合预先装入关键政策；开放调研更适合增量查询，两者可以混合。

收益应测量工具选择错误、事实支持率、成本和完成时间。工具发现本身会增加一次或多次调用；加载失败时返回缺失状态，不能假定模型已经读过材料。

## 压缩后的状态必须可验收

压缩摘要建议保留：目标、当前状态、客户已确认事项、有效事实及来源、已执行动作与回执、尚未满足的条件、预算与停止原因。原始事件保存在模型上下文之外，摘要指向原始证据。

容易失真的内容包括否定条件、金额、审批有效期以及“尚未执行”。在相同轨迹前缀上比较压缩前后行为，专门检查摘要是否把待处理事项误写成完成状态。

长期记忆应有写入规则、来源、过期与删除机制。把模型总结直接保存为永久事实，会把早期误判带入后续任务。

## 缓存要分层

| 缓存 | 缓存的对象 | 必须验证的边界 |
|------|------------|----------------|
| 模型前缀缓存 | 稳定指令、工具定义等输入前缀 | 供应商规则、有效期、命中计费与数据策略 |
| 检索结果缓存 | 某个查询的候选证据 | 租户、权限范围、知识版本与撤权失效 |
| 业务结果缓存 | 查询到的业务状态 | 新鲜度、资源版本和业务系统允许的使用期限 |
| 答案缓存 | 最终回复及引用 | 任务约束、用户可见范围与引用是否仍有效 |

模型前缀缓存通常复用计算；它不能证明外部事实仍然最新。不能用“命中缓存”作为跳过订单核验的理由。

## 对照实验

固定同一批正常、长对话、证据过期和恶意文档案例，比较全量装入、固定摘要、结构化状态加按需证据。记录输入量、补充检索次数、关键约束遗漏、任务成功与单个有效解决问题的成本。

正常案例改善但审批条件被压缩掉，应判为不可发布。
